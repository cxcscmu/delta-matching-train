# tests/: environment, data, kernel, launcher, training and evaluation checks

```
pytest tests -m "not gpu"            # any machine, no GPU: the environment and its pins, CPU logic (loaders, Muon, BOS
                                     #   options, signal handling, checkpoints and resume), the arm table, the launchers,
                                     #   the experiment driver and the Slurm chains with stand-ins, the stage-2 /
                                     #   experiment / eval-chain scripts in dry mode, the data scripts on synthetic data,
                                     #   the paired comparison; + the data root, tokenizer, RULER and caches when found
pytest tests                         # a GPU node (Hopper): + the Delta-Matching kernels vs fp32, the mixers, 3-step
                                     #   trainings of the arms, resume and launcher chains, the eval engine, HF conversion
pytest tests -m "not slow"           # skip the subprocess trainings and evaluations (minutes each), the CPU ones included
DM_TEST_GPU=3 pytest tests/test_train_smoke.py     # the GPU the subprocess smokes run on (default 0)
```

Markers: `gpu` (needs a CUDA GPU; skipped when none is visible), `slow` (launches training or evaluation
subprocesses), `data` (needs the data root; skipped when none is found and `DM_DATA_ROOT` is unset). A test that needs
the tokenizer or the data root through a fixture skips when nothing is configured and nothing is found, and fails when
`DM_DATA_ROOT` / `DM_TOKENIZER_DIR` is set but incomplete.

What the CPU subset needs: the Python environment of docs/SETUP.md section 2 (torch, transformers, lm_eval, fla, ...),
`bash`, `tar`, GNU `cp` and coreutils, and util-linux's `flock` and `setsid`. No GPU, no network, no data, no Slurm: the
launchers and experiment drivers run in their dry modes or with stand-ins, and every fake workspace, export or data file
lives in pytest's temporary directory. The stand-ins: `test_slurm_wrappers.py`'s FakeSlurm (`sbatch`, `squeue`,
`scancel` and `scontrol` sharing one queue file, which they change as slurmctld would: a scancel of a running job makes
it CANCELLED and COMPLETING with the end time of the cancel; squeue's `-O RestartCnt` prints a job's restart count,
which test_slurm_chain_stops.py raises for a requeue while the job stays COMPLETING, as Slurm 24.05.5 shows it), and
`tests/_helpers.py`'s interpreter, trainer ranks, torchrun, export check, val CE and squeue (`fake_launch_env`) and
srun, scontrol (`show hostnames`), scancel (of `<job>.<step>`: the step is cancelled) and, with `fork_setsid=True`, a
forking setsid (`fake_multinode_env`: job 4242 on the nodes fake-n0, fake-n1, ..., fake-n0 the batch host). The srun runs one node
launcher per "node" on this host and behaves as srun does on the cluster: a task that fails ends the step
(kill-on-bad-exit: a catchable SIGTERM to each task, i.e. each node launcher, never to the ranks, as Slurm signals a
step's tasks only; SIGKILL to every process of every task `FAKE_SRUN_KILL_WAIT` seconds later, Slurm's KillWait), and a
SIGTERM to srun itself SIGKILLs every task (exit 137); with `FAKE_SRUN_REPORT_<k>` task k only writes that node report
(train_arm.sh's aggregation on its own). The multi-node rank modes: `per_rank` (`FAKE_RANK_MODES`, one per global
rank: `ok`, `fail`, `failon:<flag>:<rc>` (exits with `<rc>` once the test creates the file `<flag>`), `hang` (blocked
in a collective: ignores SIGTERM) or `stop`) and `allreduce_stop` (every rank `stop`: a SIGTERM or SIGUSR1 to any
rank, as to the trainer, stops every rank of every node at the same step through a shared flag file, the trainer's
MAX-all-reduced stop flag). The CPU resume tests run the real trainer over gloo. `test_env.py` checks the pinned
versions (`env/requirements-cu130-hopper.lock.txt`), `nvcc` 13 and the `delta_matching` kernel package; the tests
that need the kernel package fail, not skip, when it is missing (docs/SETUP.md section 3: `scripts/install_kernel.sh`
installs the bundled `kernels/delta-matching`, and `test_kernel_bundle.py` checks that the installed package is that
build).

Environment variables (locations follow `scripts/campaign/env.sh`):

| variable | default | used for |
|---|---|---|
| `DM_WORKSPACE` | `<repo>/workspace` | scratch; the smoke runs write to `$DM_WORKSPACE/tests_tmp/` (removed at the end of the session) |
| `DM_DATA_ROOT` | `$DM_WORKSPACE/data` | the training / val streams, RULER, the HF caches (data/README.md) |
| `DM_TOKENIZER_DIR` | `<data root>/tokenizer/llama2_32k` | the tokenizer |
| `HF_HOME` | `<data root>/hf_cache` | the eval datasets cache |
| `DM_PY`, `DM_TORCHRUN` | the interpreter running pytest, and `torchrun` beside it | the subprocesses |
| `DM_SO` | the kernel package's own library | the delta_matching library to load; on a `DM_BF16_DP=1` build (a study variant of the kernel package) the stale / matched kernel and training tests skip, since that build refuses them by design, and the bf16_dp flag check runs in the other direction |
| `DM_EXPECT_BUNDLED_KERNEL` | `1` | `0`: the environment runs another kernel build on purpose (e.g. the original release); test_kernel_bundle.py then skips its installed-build check |
| `DM_TEST_GPU` | `0` | the GPU of the subprocess tests; in-process GPU tests (test_kernels, test_new_mixers, test_muon, test_env) use GPU 0 of `CUDA_VISIBLE_DEVICES` |
| `DM_KEEP_TEST_RUNS` | `0` | `1` keeps `$DM_WORKSPACE/tests_tmp/` |
| `DM_TEST_EVAL_CONFIG` | `tiny_hybrid.yaml` | the tiny yaml of `tests/configs` whose export the eval and HF conversion tests use (e.g. `tiny_kda.yaml`) |
| `DM_TEST_BASH` | unset | a second bash (e.g. the training image's 5.2) for test_launcher_signals.py |

The subprocesses never inherit the launcher, trainer, kernel, evaluator or Slurm knobs of the calling shell (`DM_*`
except the kernel library's location `DM_SO`, `DM_JIT_DIR`, `DM_FA_SRC`; `S2_*`, `SLURM_*`, `SEEDS`, `DRY`, `TAG`,
`EXTRA_ARGS`, `SMOKE`, `STOP_AT_STEP`, `NUM_STEPS`, `EVAL_ENGINE`, the rank variables, ...): each test sets the ones it
needs (tests/_helpers.py `base_env`, `dry_env`), so a test run inside a Slurm job or a chain never takes the job's
identity or writes the chain's progress. The dry launcher checks also run with every GPU hidden (`CUDA_VISIBLE_DEVICES`
empty).
